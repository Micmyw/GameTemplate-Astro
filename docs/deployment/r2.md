# R2 game release workflow

This guide describes the manual release process for static game packages. The
SEO site does not contain game builds, does not bind an R2 bucket, and does not
upload to R2 during its build. Run every command in this document only from a
trusted operator workstation or an explicitly approved CI job.

No production upload or secret configuration is performed by this repository.

## Known routing blocker

The intended public game URL is:

```text
https://play.example.com/<slug>/
```

The intended entry object is:

```text
<slug>/index.html
```

Cloudflare's current public-bucket documentation does not document an automatic
directory index or a rewrite from `/<slug>/` to `/<slug>/index.html`. R2 is a
flat object store: an object is identified by its key, and `/` only groups keys
by prefix in tools and the dashboard. Connecting a custom domain exposes the
bucket; it does not document a website-style routing layer.

Therefore, without a separately configured Worker or other routing rule, the
currently supportable exact-key URL is:

```text
object key: <slug>/index.html
public URL: https://play.example.com/<slug>/index.html
```

Do **not** claim that either of these mappings exists automatically:

```text
/<slug>/                       -> <slug>/index.html
/<slug>/                       -> games/<slug>/current/index.html
```

The content schema currently requires an embed path ending in `/`, so the
exact-key `/index.html` URL is not a production-ready substitute. Production
publishing remains blocked until one of these choices is reviewed and tested:

1. Add an independently approved routing layer that maps `/<slug>/` to the
   exact `<slug>/index.html` key.
2. Deliberately change the public URL and the validated content contract to use
   `/<slug>/index.html`.

PR 4 does not add a Worker, rewrite, R2 binding, or production route. Until the
decision is made, `https://play.example.com/<slug>/` is an intended stable URL,
not proof that the underlying R2 object is reachable at that URL.

See Cloudflare's [R2 objects documentation](https://developers.cloudflare.com/r2/objects/)
and [public buckets documentation](https://developers.cloudflare.com/r2/buckets/public-buckets/).

## 1. Create and expose the bucket

Create a dedicated bucket in the production Cloudflare account. `<...>` values
below are placeholders and must never be committed with real credentials.

```sh
npx wrangler login
npx wrangler r2 bucket create <BUCKET>
npx wrangler r2 bucket list
```

The same operation is available from **R2 object storage** in the Cloudflare
dashboard. See Cloudflare's [R2 CLI guide](https://developers.cloudflare.com/r2/get-started/cli/).

Connect `play.example.com` from the bucket's **Settings > Custom Domains**
screen. The domain's zone must be present in the same Cloudflare account as the
bucket; follow Cloudflare's documented partial CNAME setup when the zone is not
otherwise managed there.

Use `r2.dev` only for temporary development verification. It is documented as
a rate-limited, non-production endpoint, and a CNAME pointing at it is an
unsupported access path. Custom-domain and `r2.dev` access are independent, so
after `play.example.com` is active, disable the **Public Development URL**. A
disabled `r2.dev` endpoint does not disable the custom domain.

The custom domain is also the supported path for Cloudflare Cache, WAF, access
controls, and Bot Management. Do not describe those features as available on
the development URL.

## 2. Create least-privilege credentials

AWS CLI and rclone use R2's S3-compatible API. In **Manage R2 API tokens**:

1. Create an **Object Read & Write** token.
2. Scope it to the one game-assets bucket, not every bucket in the account.
3. Record the Access Key ID and Secret Access Key in the operator's credential
   store or approved CI secret store. The secret cannot be viewed again.
4. Never paste either value into Markdown, shell history, screenshots, issue or
   PR comments, validator output, or Git-tracked files.

The standard S3-compatible endpoint is:

```text
https://<ACCOUNT_ID>.r2.cloudflarestorage.com
```

Jurisdictional buckets require their documented jurisdiction-specific
endpoint. Do not assume one client configuration can address multiple
jurisdictions.

See [R2 authentication](https://developers.cloudflare.com/r2/api/tokens/).

### rclone

Run `rclone config`, select the Amazon S3-compatible storage type, select
Cloudflare R2 as the provider, and supply the endpoint. Prefer retrieving the
credentials from the runtime environment or local credential store. For an
object-level token, Cloudflare documents that the remote also needs:

```ini
no_check_bucket = true
```

The configuration name `r2` used below is only an example. See Cloudflare's
[rclone guide](https://developers.cloudflare.com/r2/examples/rclone/).

### AWS CLI

Configure a dedicated profile without writing credentials into this repository.
R2 accepts `auto` as the AWS CLI region. Every example must point at the R2
endpoint explicitly or use an operator-owned profile that already contains it.

See Cloudflare's [AWS CLI guide](https://developers.cloudflare.com/r2/examples/aws/aws-cli/).

## 3. Object-key convention

R2 has no real folders. These are object-key prefixes chosen by this project:

```text
# Exact live keys
<slug>/index.html
<slug>/assets/<content-hashed-file>

# Immutable release record
_releases/<slug>/<version>/index.html
_releases/<slug>/<version>/assets/<content-hashed-file>
_releases/<slug>/<version>/release-manifest.json
```

Do not use `games/<slug>/current/` and imply that it maps to `/<slug>/`.
Without an explicit router, it is just another literal key prefix.

Keep asset references in `index.html`, CSS, and JavaScript relative to the game
package. A release entry must never point to an asset that has not already been
uploaded and verified.

## 4. Validate before any upload

Keep the game build outside this repository's `src/` and `public/` directories.
Run the local, credential-free validator first:

```sh
npm run game:validate -- <LOCAL_PACKAGE>
```

Choose an operator-approved maximum when required:

```sh
npm run game:validate -- <LOCAL_PACKAGE> --max-file-mb <MAX_FILE_MB>
```

The threshold is a release-policy input, not a permanent Cloudflare platform
limit. Do not restore the obsolete `315 MB Wrangler limit` language or hardcode
a mutable provider limit. Consult the live [R2 limits](https://developers.cloudflare.com/r2/platform/limits/)
when planning a real transfer.

Stop on every validator error. Review every warning, including external scripts,
network requests, `window.open`, external forms, dynamic resource loading, and
large non-hashed assets. A warning is not an approval.

## 5. Record the release

Before uploading, create a release record outside the game package or as
`release-manifest.json`. It must contain:

- game slug;
- version;
- upstream source name and HTTPS URL;
- license or written permission basis;
- build date;
- validator command, result, and validator version/commit;
- a hash for every file, or the location of a signed/controlled hash manifest.

Do not publish a game whose source or redistribution rights are unknown.

## 6. Upload assets before the entry HTML

Use a unique version and content-hashed filenames. Never overwrite a hashed
asset with different bytes.

The following intentionally placeholder-only command records a complete release
under the archive prefix. It does not make the release live:

```sh
rclone copy "<LOCAL_PACKAGE>" "r2:<BUCKET>/_releases/<SLUG>/<VERSION>/" --progress
rclone tree "r2:<BUCKET>/_releases/<SLUG>/<VERSION>/"
```

For the live prefix, first upload **every package file except `index.html`**.
This includes root-level manifests or level files and any `images/`, `audio/`,
or other directories; do not assume that every dependency lives under
`assets/`. Use a reviewed short cache policy as the safe default:

```sh
aws s3 cp "<LOCAL_PACKAGE>/" "s3://<BUCKET>/<SLUG>/" \
  --recursive \
  --exclude "index.html" \
  --endpoint-url "https://<ACCOUNT_ID>.r2.cloudflarestorage.com" \
  --cache-control "public, max-age=3600"
```

After that complete non-entry upload, set long-lived metadata only on files
whose names and release manifest prove they are content hashed. Repeat this
placeholder command for each verified hashed file, preserving its relative key:

```sh
aws s3 cp "<LOCAL_PACKAGE>/<HASHED_RELATIVE_PATH>" \
  "s3://<BUCKET>/<SLUG>/<HASHED_RELATIVE_PATH>" \
  --endpoint-url "https://<ACCOUNT_ID>.r2.cloudflarestorage.com" \
  --cache-control "public, max-age=31536000, immutable"
```

`31536000` is this project's one-year cache policy in seconds, not an R2
object size, rate, or availability limit. A non-hashed asset must retain a
shorter reviewed cache policy or be renamed with a content hash before release.

R2's S3 compatibility table documents `Cache-Control` as supported system
metadata for `PutObject`, multipart upload creation, and `CopyObject`. See
[S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/).

## 7. Verify assets through the storage API

R2 writes, metadata changes, listings, and same-bucket copies are strongly
consistent through the storage APIs. Check the expected keys before publishing
the entry HTML:

```sh
aws s3api list-objects-v2 \
  --bucket "<BUCKET>" \
  --prefix "<SLUG>/" \
  --endpoint-url "https://<ACCOUNT_ID>.r2.cloudflarestorage.com"

aws s3api head-object \
  --bucket "<BUCKET>" \
  --key "<SLUG>/assets/<HASHED_ASSET>" \
  --endpoint-url "https://<ACCOUNT_ID>.r2.cloudflarestorage.com"
```

Compare the complete non-entry key list, reported sizes, and checksum/ETag
evidence with the release manifest as appropriate for the upload method. Verify
every file referenced by the new `index.html`, including files outside
`assets/`; do not infer completeness from one successful object.

## 8. Upload `index.html` last

Only after all referenced assets exist, upload or replace the exact live entry:

```sh
aws s3 cp "<LOCAL_PACKAGE>/index.html" "s3://<BUCKET>/<SLUG>/index.html" \
  --endpoint-url "https://<ACCOUNT_ID>.r2.cloudflarestorage.com" \
  --content-type "text/html; charset=utf-8" \
  --cache-control "no-cache"

aws s3api head-object \
  --bucket "<BUCKET>" \
  --key "<SLUG>/index.html" \
  --endpoint-url "https://<ACCOUNT_ID>.r2.cloudflarestorage.com"
```

`no-cache` permits storage but requires revalidation; an explicitly reviewed
short `max-age` is another option. Do not give `index.html` the immutable asset
policy.

Verify the currently documented exact-key public URL:

```sh
curl --fail --show-error --head \
  "https://play.example.com/<SLUG>/index.html"
```

Also open the game in a browser and test its controls, console, mobile layout,
and iframe sandbox behavior before changing its content status to `published`.

Do not test `https://play.example.com/<SLUG>/` and treat success as guaranteed
until the separate short-path router has been configured and independently
verified.

## 9. Cache behavior and invalidation

A custom domain can use Cloudflare Cache. Cloudflare documents that only its
default cacheable file types are cached unless a reviewed Cache Everything rule
is added. Object `Cache-Control` metadata alone is not proof that every file type
received an edge-cache hit.

Caching relaxes the direct R2 consistency guarantee:

- an overwritten key can continue serving the previous object until TTL expiry,
  eviction, or purge;
- a cached 404 can remain after the missing object is uploaded;
- deleting an object does not remove an already cached response.

Prefer immutable hashed asset URLs. Purge the entry URL after an urgent switch
or rollback when immediate visibility is required. Follow Cloudflare's
[cache purge documentation](https://developers.cloudflare.com/cache/how-to/purge-cache/)
and keep any purge API token in a secret store.

See the [R2 consistency model](https://developers.cloudflare.com/r2/reference/consistency/).

## 10. Roll back the entry

Keep prior hashed assets and prior release records. A rollback restores a known
stable archived `index.html`; it must not point to assets that have been deleted.

R2 supports same-bucket `CopyObject`, `Cache-Control`, and metadata replacement:

```sh
aws s3 cp \
  "s3://<BUCKET>/_releases/<SLUG>/<PREVIOUS_VERSION>/index.html" \
  "s3://<BUCKET>/<SLUG>/index.html" \
  --endpoint-url "https://<ACCOUNT_ID>.r2.cloudflarestorage.com" \
  --metadata-directive REPLACE \
  --content-type "text/html; charset=utf-8" \
  --cache-control "no-cache"
```

Then:

1. `head-object` the restored live key.
2. Purge the affected custom-domain entry URL if immediate change is required.
3. Load the game in a browser and confirm the restored asset requests succeed.
4. Record the rollback version, operator, time, reason, and validation result.

Do not delete the failed release during incident response. Preserve its manifest
for diagnosis unless legal or security requirements demand removal.

## 11. Security rules

- Game code must not depend on cookies belonging to the SEO site's origin.
- Game code must not navigate the top-level browsing context.
- Do not enable broad CORS by default. Add the narrowest policy only when a
  documented cross-origin browser request requires it.
- Never put R2 credentials in the repository, game package, command examples,
  validator output, build logs, browser code, or PR evidence.
- R2 credentials are configured only by the operator in local credential storage
  or by an approved CI secret store.
- This PR creates no R2 binding, Worker rewrite, real secret, upload automation,
  or production deployment.

## 12. Add the final URL to game content

Do this only after the routing blocker at the top of this document is resolved
and the chosen public URL passes browser verification.

- With an independently deployed and verified short-path router, use
  `https://play.example.com/<slug>/`.
- With direct exact-key R2 access, the documented path is
  `https://play.example.com/<slug>/index.html`, but adopting it requires an
  approved change to the current trailing-slash embed URL contract.

The Origin alone, such as `https://play.example.com`, belongs in
`PUBLIC_GAME_ORIGINS`. Never place a path, query, fragment, username, or password
in the Origin allowlist.
